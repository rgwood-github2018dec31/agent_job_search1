# Requirements

## Actors

- **User** — the job seeker; runs the agent and provides feedback on job postings
- **Scheduler** — a scheduled system event (e.g. cron) that triggers autonomous runs; a kind of User with no interactive input
- **LinkedIn** — external job board; serves search results and job pages (secondary actor)
- **Telegram** — external messaging service; delivers notifications to the User (secondary actor)
- **OpenRouter** — external paid LLM gateway (via MCP tool server :8006); summarizes reference jobs and optionally rates fit (secondary actor)
- **Local LLM** — local Ollama models (via MCP tool server :8002); triages job fit for free and serves as summarization fallback (secondary actor)
- **Exchange Rate Service** — external public service publishing daily currency rates (`FX_RATES_URL`); supplies the rate behind a converted salary figure (secondary actor)

## Business Object Model

- **Resume** — user's CV stored as Markdown in `run_dir/`
- **Preferences** — `run_dir/preferences.yaml` (gitignored), loaded by `preferences.py`: the `save_dir` where saved job PDFs land (default `~/Downloads`), search regions (each with a `linkedin_location` typed into the location chip and an optional `geo_id` used only to verify the click landed), sponsorship-required locations, languages, `foreign_language_rating_cap`, rejected degree levels, the hybrid/on-site rating cap, the geographic gate as **three place lists** — `locations.would_live_here` (exempts), `would_not_live_here` (rejects) and `not_yet_bucketed` (the agent's guesses, which gate nothing) — plus `would_commute_here`, a different question driving the hybrid/on-site cap only; all proper names, matched case-sensitively and accent-exactly, target/excluded titles, relocation note, **`current_tax_residence`** (the one country the person lives in today, a proper name; empty by default), the **base salary target** (`compensation.base_target` with its ISO `compensation.currency`; both unset = no code-side comparison), the **salary conversion** (`compensation.convert_to`, the ISO currency a foreign-currency salary is additionally shown in, and `compensation.keep_currencies`, the currencies left as written; `convert_to` unset = nothing is converted), and the **company blacklist** (`companies.blacklist`: per entry a `name`, a `reason`, and an `added` date; entries expire after `COMPANY_BLACKLIST_EXPIRY_DAYS`). This is the **only** home for facts about the person running the agent; tracked source must stay neutral. `preferences.example.yaml` in the project root documents the format with placeholder values
- **JOB_REQUIREMENTS.md** — agent-managed preference file; read-only in non-interactive mode
- **Search Query** — short LinkedIn search string derived from Resume, JOB_REQUIREMENTS.md, and Applied Job Records
- **Applied Job Record** — a job the User applied to: a date-prefixed PDF in `run_dir/applied_jobs/` plus its `index.yaml` metadata (applied date, company, job title, recruiting-agency flag, end client, and the extracted text **per page**, `pages`; entries written before 2026-09-21 hold one joined `text`, read as a single page). Active for `APPLIED_JOBS_HORIZON_DAYS`; older records are retained but unused
- **Job Posting** — a LinkedIn listing with company, title, description, URL, job_id, date_posted, `workplace_type` (`remote` / `hybrid` / `onsite`), `education_requirement` (`master` / `phd` / empty — hard requirements only), `posting_language` (the language the **source page** is written in), `likely_working_language` (the language a professional team at the job's location most likely works in, from the classifier — never from the posting), `stated_working_language` (the language the posting **says** the team works in, from the extractor — empty unless stated), `place_names` (every other name the location's places go by, English and local, from the classifier), `residency_scope` (`country_only` / `area_wide` / empty — whether the JD pins residence to the anchor country, offers a whole multi-country area, or says nothing; **not** the same as the anchor), `is_agency` (poster is a staffing firm / aggregator, not the employer) and `end_client` (who would actually hire, when the posting names them; empty when the poster echoes itself back), `salary` (the compensation **as the posting states it** — both ends of a range, currency and period, never rounded and never one-ended when the page gives two; the contract is `SALARY_FIELD_DESCRIPTION`, shared by all three extract schemas), and a 1–5 rating
- **Salary Reading** — what a Job Posting's free-text `salary` states, derived in code: a `kind` (`absent` / `floor_only` / `ceiling_only` / `single` / `range` / `unclassified`), the bounds, currency and period it could resolve, the text as written, and a `source` (`deterministic` / `cache` / `llm` / `error` / `unverified`). Cached in `run_dir/salary_cache.yaml` by normalized salary string, so one phrase is read once and cannot be answered two ways. **Decides no policy** — which readings warn is a table in code
- **Salary Conversion** — a Salary Reading's (or Salary Estimate's) bounds in the Preferences `compensation.convert_to` currency: the converted bounds, the source currency, the rate and the rate's date. Computed in code from the Exchange Rate Service's table (`run_dir/fx_rates_cache.yaml`, one table per day). **Display only, and always beside the original**: it appears on the `💰` line and in the Saved Job, and nothing compares it against anything
- **Salary Estimate** — a model's pay range for a Job Posting whose Salary Reading is `absent`: bounds, ISO currency, period, a one-line basis, and the model that produced it. Kept in `run_dir/salary_estimate_cache.yaml`, one entry per job ("cannot estimate" included), which is mostly an audit record of what was shown. **Not a Salary Reading and never merged into one**: it is not something the posting states, it is always labelled as an estimate, and it decides nothing
- **Raw Posting Capture** — the page an extract was made from, kept at `run_dir/raw_postings/{date}/{site}-{job_id}.txt` behind a provenance header (url, job_id, capture time, which extract path, chars captured vs chars sent to the model), capped at `RAW_POSTING_MAX_CHARS` and pruned to `RAW_POSTINGS_RETENTION_DAYS`. **Read by nothing in the pipeline** — no gate, no rating, no dedup. It exists so a figure an extract reports can be checked against the page it came from; a failure to write one is logged and the run continues
  - Since 2026-09-24 the `.txt` holds exactly the text the extractor read: the de-cluttered page (`source: dom`), or the budgeted accessibility snapshot on the fallback (`source: snapshot`). That is what Check Salary Provenance compares a figure against. Beside it, `{site}-{job_id}.html` archives the **whole** page as captured, JS-free, with the posting company's logo linked from Company Assets, every other image blanked (people's photos are never stored), and the stylesheet stored once per day under `{date}/assets/`.
- **Company Asset** — the posting company's logo, stored once per company under `run_dir/company_assets/{Company Name}/` (the name as written), named by content hash and indexed by URL, so a later page reuses it instead of fetching again. Fetched with plain `requests` from LinkedIn's public CDN, never through the logged-in browser. Gates nothing.
- **Page Section Decision** — an entry in `run_dir/linkedin_page_sections.yaml` for a LinkedIn job-page section code could not place: keyed by signature (its heading or first line, digits as N, at most `PAGE_SECTION_SIGNATURE_MAX_WORDS` words), with `decision` (`remove` / `keep`), the model's reason, `decided_by`, the date, the first job it was seen on, and a sample. Written by the agent the first time a signature appears; the user edits `decision` to overrule it. An unreadable file is left untouched and every unknown section is kept.
- **Location Guess** — an entry the agent appends to `locations.not_yet_bucketed` for a country none of the user's lists names: the country, plus a YAML comment carrying the date, the guess (`would live` / `would NOT live`) and a one-line reason. **Gates nothing** — the user moves it into `would_live_here` or `would_not_live_here` by hand
- **List Hygiene Finding** — an `entry_warnings` record in `run_dir/location_recommendations.yaml` naming an entry on the user's place lists that is ambiguous (`collision`: it sits inside another place, `Roma` in `Romania`) or dead (`dead_entry`: it never matches, but would with its case or accents fixed), with a user-owned `status` (`pending` / `accepted` / `rejected`). **Written by the agent, never read as policy**
- **Rating** — the evaluator's verdict on a Job Posting: 1–5 score, reasoning, filename label, plus **pros** and **warnings** bullet lists that drive the Notification and the Saved Job
- **Processed Job Record** — `processed_jobs/*.yaml` keyed by `(site, job_id)`; drives deduplication across runs. Written when Stage 1 queues the job, and deleted again only by Recover Browser for a job Stage 2 never reached
- **Recruiter Notification Record** — an entry in `run_dir/recruiter_notifications.yaml` for one agency posting the User was **notified** about: the agency as written plus a folded `agency_key`, `job_id`, title, location, salary, end client, the date, and the condensed description capped at `RECRUITER_DESCRIPTION_MAX_CHARS`. Pruned to `RECRUITER_REPOST_WINDOW_DAYS` on every read. **Gates nothing else** — no rating, no rejection; it exists only so a second notification for a role already sent can be withheld. Recomputable, so unlike `location_recommendations.yaml` a corrupt file is treated as empty rather than preserved
- **Saved Job** — evaluated posting stored as `saved_jobs-{date}/job_posting-{id}-rating_{n}-*.md`

## Use Cases

**User**
- **Run interactive review**: present Job Postings one at a time and collect feedback
  - includes: Evaluate Job Fit
  - includes: Refine Job Requirements
- **Refine Job Requirements**: rewrite JOB_REQUIREMENTS.md based on User feedback on a Job Posting

**Scheduler**
- **Run autonomous search**: discover and rate Job Postings without user interaction
  - includes: Ingest Applied Jobs
  - includes: Generate Search Queries
  - includes: Scrape Job Postings
  - includes: Evaluate Job Fit

**System** (invoked via includes)
- **Categorize Saved PDFs**: label each not-yet-categorized PDF in the save directory with one cheap `ANTHROPIC_MODEL_NAME_LOW` call and rename it `cat-<label>-…`. The PDF text is sent **per page** through `pages_to_prompt()` under `PDF_PROMPT_MAX_CHARS`, which is derived from the model's context window. Every PDF logs its page count and chars per page. Over the cap, whitespace is normalized first (WARNING), and only if still over is the text truncated (a second WARNING, a console warning, and a marker telling the model). An API-level failure aborts the run rather than repeating per file (see Resilience)
- **Ingest Applied Jobs**: move categorized applied-job PDFs from the configured save directory (`save_dir` preference) into `run_dir/applied_jobs/`, stamping each filename with its applied date and preserving mtime; already-dated files are a no-op, so it is safe on every run
  - includes: Categorize Saved PDFs
  - includes: Flag Recruiting Agency
- **Flag Recruiting Agency**: record whether an **Applied Job Record's** poster is a staffing firm or aggregator rather than the hiring employer, along with the end client if named; agency names are never added to the already-applied blocklist
- **Generate Search Queries**: derive at most `MAX_SEARCH_QUERIES` Search Queries from Resume, JOB_REQUIREMENTS.md, and the Applied Job Records within `APPLIED_JOBS_HORIZON_DAYS` (glm, Anthropic fallback), covering both the titles already applied to and adjacent titles. Individual-contributor titles only — people-management titles (Manager / Head of / Director / VP) are excluded
- **Write Run Audit Log**: at the end of every run, write `run_dir/audit_logs/audit-{date}-{time}.md` tracing applied-job counts, every Search Query and whether it was actually searched, listings and candidates per query **broken down by check status (new / already processed / already applied / too old)**, and the outcome of every individual Job Posting with its URL and summary. The per-query breakdown is what separates a dedup-saturated query from one that barely ran. §1 also reports the active blacklist count and names every **expired** blacklist entry with its date — an entry that quietly stopped rejecting is exactly the kind of change that otherwise goes unnoticed for months
- **Screen Candidate Title**: at queue time, deterministically ($0) skip a listing whose title is below target seniority (intern / junior / entry-level / new grad / apprentice / trainee / co-op) or matches a Preferences `titles.exclude` word, before it reaches the paid extract-and-rate path. Conservative by design — word-boundary matches only, `associate` and bare `graduate` never reject, and work arrangement is never judged from a search card. Every skip is logged and counted in the run funnel under `queue_skipped`; extends Scrape Job Postings
- **Audit Un-surfaced Jobs**: (`--audit-opus N`) sample N Job Postings from each of three un-surfaced pools — filtered at Stage 1, seen but never queued, and rated 2–3 — re-rate each with Opus, and report any the strong model scores ≥4 as a false negative. Diagnostic only; nothing is saved or notified
- **Scrape Job Postings**: execute Search Queries on LinkedIn and collect candidate Job Postings. Every Search Query runs as **one search per configured region** (see Preferences `search_regions`), and all of them run every time.

  **Filters are set by CLICKING the filter chips, never by putting them in the URL and never in the query text.** Each search navigates to `/jobs/search-results/?keywords=<QUERY>, remote&f_SAL=` — a bare keyword URL, which is what a bookmarked or shared LinkedIn search looks like — and then clicks: the **location chip** (clear, type the region, pick the autocomplete suggestion), **Date posted** → `SCRAPER_DATE_POSTED_LABEL`, and **Experience level** → `SCRAPER_EXPERIENCE_LABEL`. The empty `f_SAL=` stays, because the account-level salary filter self-injects.

  Two things this replaces, both wrong: putting the region in the **query text** (silently ignored — every EU search returned the home metro for days), and navigating **directly to `geoId=`/`f_TPR=`** (works, but no human assembles filter parameters by hand, so it is a cheap fingerprint for anti-automation). The `geo_id` preference exists **only** to read back afterwards and confirm the click landed. Sort order is not a coverage axis — the UI exposes no sort control. Region is.

  **A reply with no tool call is not "finished" until something has been recorded** (2026-09-28). The OpenRouter loop ended a query the moment the model answered with text alone, so one sentence of intent ("I'll start by navigating…") closed a query after 2 iterations; it recurred on 2026-09-29 and 2026-10-02. Before the first completed `record_listings`, such a reply gets the fixed `NO_TOOL_NUDGE` message and the conversation continues, at most `SCRAPER_NO_TOOL_NUDGES` times per pass. Never after a block signature or a `report_problem`: stopping there is correct (see Account safety).

  **Region verification and `stopped_early` are judged on the query's final state, after the recovery pass** (2026-09-28). The `unverified_search` check ran before the recovery pass and was never withdrawn, so a query whose recovery pass verified both regions and harvested 50 listings still read SEARCH NOT VERIFIED and STOPPED EARLY. A short first pass that recovery completed — at least `SCRAPER_MIN_LISTINGS_PER_QUERY` distinct listings and every region verified — is logged, not alerted.

  Searches are **expected to return a high proportion of `already_processed`** results — that is the cost of the few genuinely best-matching jobs they surface, and is not a failure signal. Only page 1 is scanned. The converse also holds: **two searches returning the identical list of jobs means the location filter did not apply**, and is a failure to report rather than a sign the query is exhausted — now measured in code as `region_overlap` rather than left to the model to volunteer.
  - includes: Verify Search UI Contract
  - includes: Harvest Job Listings
  - includes: Pin Scraper Provider

  A search returning zero results is retried once before being counted as empty. A query inspecting fewer than `SCRAPER_MIN_LISTINGS_PER_QUERY` **distinct** listings is retried once by `run_scraper`: at **zero** (auth-wall / block / empty-shell signature, distinct from "seen but deduped") the retry drops the location filter; **above zero** — the signature of a results list that was never walked — the retry re-states the harvest procedure. Counting **distinct** listings rather than `check_and_record_job` calls is load-bearing: two regions returning the same 25 cards used to read as 50 and pushed a collapsed query *further* from this threshold. **A challenge or verification page is never retried into**: the recovery prompt tells the model to stop and report instead, because pushing through a block is the one failure that can cost the account.

- **Pin Scraper Provider**: at the start of Stage 1b, list `MODEL_NAME_SCRAPER`'s OpenRouter endpoints (the tool server's free `list_endpoints`) and pin the run to the one with the lowest **effective** price for the scraper's token mix (`SCRAPER_CACHED_PROMPT_SHARE`, `SCRAPER_COMPLETION_TOKENS_PER_PROMPT_TOKEN`) among those that are up, support tools and serve at least the model's `SCRAPER_MIN_BITS_PER_WEIGHT` precision. That ranked list is the run's fallback order. A scraper model with no entry there **fails fast at startup**, before any LinkedIn traffic — there is deliberately no default. Every scraper call of the run passes the endpoint as `chat(provider=..., quantization=...)`, fallbacks off; naming the quantization is what lets a precision other than the server's default be used at all. Until 2026-09-29 only the server's *default* precision was eligible: when that became bf16, one endpoint qualified, and a single 429 on 2026-09-27 and -28 had nowhere to switch and dropped Stage 1b to the Anthropic scraper while 10+ fp8 endpoints were up. A provider-side failure — including a 429, which on a pinned endpoint is that provider's rate limit — moves the run to the next-cheapest endpoint, at most `SCRAPER_PROVIDER_MAX_SWITCHES` times, with a WARNING and a run alert; an account failure (`ACCOUNT_LEVEL_HTTP_STATUSES`) still aborts to the Anthropic scraper. If no endpoint can be chosen the run goes unpinned, with a run alert. Each query logs the provider that served it and its effective $/M prompt tokens, and alerts above `SCRAPER_COST_ALERT_FACTOR` times the estimate
- **Verify Search UI Contract**: on every search, run one read-only `browser_evaluate` (`SCRAPER_UI_CONTRACT_JS` in `agent.py`) reporting the page's structure — search box, results container, distinct job-card count, chip row and its labels, location pin, pagination, result-count text. On both scraper paths the model calls **`run_ui_contract(region)`** and code runs the JS, reads the result and judges it: **code reads, code judges, the model only triggers.** The Anthropic fallback serves the OpenRouter scraper's own tools (`make_anthropic_scraper_server`), running the same `ScrapeSession.dispatch_local` code over Python's own session to the shared browser. **Both scrapers read one prompt, so they must serve the same tools**: from 2026-08-31 the prompt named tools the fallback did not have, and on the 2026-09-27/28 fallbacks the model improvised — searches went unverified and `report_search` received a report the model made up. `test_every_tool_a_scraper_prompt_names_is_served_by_both_scrapers` checks the system prompt and both recovery prompts. `report_search` checks, in this order:

  1. **Block signature** (`UI_BLOCK_SIGNATURES`: CAPTCHA, "unusual activity", verification, forced re-login) — checked *first* because a challenge and a markup change demand opposite responses. The query stops and is **never retried into**.
  2. **Contract violations** (`evaluate_ui_contract`) — a required `UI_CONTRACT_ELEMENTS` entry missing, or zero cards while the page itself reports results, which is the precise shape of a silent failure that otherwise reads as "no new jobs today". The query stops, the user is alerted, **remaining queries still run**.
  3. **Filter confirmation** (`check_filters_applied`) — the `geo_id` and `f_TPR=r<seconds>` the clicks should have produced are present in the URL, and the chips have relabelled to their chosen values. This is the only use of those parameters.
  4. **Fingerprint drift** (`check_fingerprint_drift`) — the chip labels are compared against `run_dir/ui_fingerprint.yaml` and any change is reported *even when every required element still passes*, so a restructure is noticed the run it happens rather than months later. Only `UI_STRUCTURAL_CHIPS` count, and a chip LinkedIn shows on some searches and not others is left out of it ("In my network" flapped within single runs, 2026-09-28); the stored fingerprint is filtered the same way, so dropping a chip does not read as "gone". **A chip is fingerprinted under its own name, never its chosen value** (`UI_CHIP_CHOSEN_VALUES`): on 2026-10-02 a page whose filters had not been set rewrote the fingerprint to the unchosen labels, and the next healthy run (2026-10-05) reported "new chips ['Past week', 'Senior']; chips gone ['Date posted', 'Experience level']". Whether a filter is set is `check_filters_applied`'s question, not the page's shape.

  Selectors for this page **must be verified against the live page before being trusted**: writing them from the accessibility tree alone produced two failures that would have broken every query (the search box is a plain `<input>` with a placeholder and no `aria-label`; cards *and* chips are each rendered twice in the DOM). Invoked by Scrape Job Postings

- **Harvest Job Listings**: read every listing off the results page in **one read-only `browser_evaluate`** (`SCRAPER_HARVEST_JS` in `agent.py`), returning id, title, company, location and posting date per card. On both scraper paths the model calls **`harvest_listings()`** (no arguments): code runs the canonical JS, keeps the listings, and returns only a count — so the model can neither retype the JS wrongly (it corrupted the contract JS this way on 2026-08-21) nor relay job data. **`record_listings()`** then records from code's copy via `do_record_listings`, which enforces `SCRAPER_MAX_LISTINGS_PER_SEARCH` **in code** (previously a prompt suggestion) and returns counts only. Cards are `div[componentkey="job-card-component-ref-<jobId>"]` inside `div[componentkey="SearchResultsMainContent"]` — **the LinkedIn job id is the attribute suffix**, so no clicking is needed to identify a listing. Cards appear twice in the DOM (dedupe by id) and each label is rendered twice (a visually-hidden copy carrying "(Verified job)" plus the visible one), so the extractor collapses both. **Nothing in the results list is ever clicked** — see Account safety. If the harvest returns an error or zero jobs while the page visibly shows results, the markup has changed and the scraper must say so rather than fall back to clicking. Capped at `SCRAPER_MAX_LISTINGS_PER_SEARCH`; invoked by Scrape Job Postings

  **Scraping is not a deterministic problem and must stay LLM-driven.** It is tempting to
  replace the agentic scraper with a parser: at any single moment the mechanics *are*
  reproducible in code (navigate → scroll the inner results container → snapshot → regex →
  click Next). That reproducibility is a snapshot of one day's markup. Job boards restructure
  their DOM without notice and will almost certainly keep adding bot detection, consent
  interstitials, login walls, and challenge pages. A hard-coded parser fails *silently* against
  all of those — it returns zero listings, which is indistinguishable from "no new jobs today".
  An LLM navigating the page can recognise an obstacle and work around it. Accordingly the
  scraper keeps the browser tools needed to handle the unexpected (`fill_form`, `type`,
  `hover`, `select_option`, `handle_dialog`, `console_messages`) even though none are used on
  the happy path, and `SCRAPER_DISALLOWED_BROWSER_TOOLS` removes only tools that are redundant
  with an untruncated snapshot or have no role in reading a results list. Cost work on Stage 1b
  should reduce what enters the model's context, never remove the model's ability to navigate
  - includes: Deduplicate Job Posting
  - includes: Filter Stale Job Posting
- **Deduplicate Job Posting**: skip a Job Posting already present in Processed Job Records, or whose company is on the already-applied blocklist derived from in-horizon Applied Job Records
- **Filter Stale Job Posting**: skip a Job Posting whose scraped date is older than `JOB_MAX_AGE_DAYS`
- **Summarize Reference Jobs**: distill the **most recently applied** `MAX_REFERENCE_JOBS` Reference Job PDFs into a compact ideal-role profile via provider chain (OpenRouter → Local LLM → Anthropic), cached until those PDFs change. Each PDF enters the prompt **whole** (`REFERENCE_JOB_PROMPT_MAX_CHARS` is sized above the largest), after `strip_saved_page_furniture()` drops whole lines of LinkedIn UI (`LINKEDIN_PDF_FURNITURE_LINE_PATTERNS`). Nothing is cut by position: the saved page's text is two-column and interleaved, so posting text — once a salary range — can sit after the sidebar's first line. The prompt tells the model to ignore the sidebar's other-job listings instead. Until 2026-09-29 the budget kept only page 1 and the description's opening, so every profile was distilled from headers and Premium upsells. Newest-first ordering is load-bearing, not cosmetic: the cap is applied with a plain slice, so the sort order decides which ones the rater ever sees
- **Evaluate Job Fit**: extract, filter, triage, and rate a candidate Job Posting, saving it as a Saved Job
- **Recover Browser**: when the shared `@playwright/mcp` process has died, restart it on a fresh port, up to `PLAYWRIGHT_MAX_RESTARTS_PER_RUN` times per run, and retry the Job Posting it died on. Once that budget is spent, stop Stage 2 and release every unevaluated Job Posting by deleting its Processed Job Record, so the next run evaluates it; extends Evaluate Job Fit
  - includes: Extract Job Posting
  - includes: Flag Agency Posting
  - includes: Deduplicate by End Client
  - includes: Apply Hard Rules
  - includes: Reject Blacklisted Company
  - includes: Triage Job Posting
  - includes: Rate Job Fit
  - extends: Recover Browser
  - includes: Notify User of Match
  - extends: Suppress Recruiter Repost
- **Extract Job Posting**: capture a condensed, information-dense extract of the Job Posting's page; route and model configurable via `MODEL_NAME_EXTRACTOR`. On the default OpenRouter route, code reads the page first and the model gets its text and **one tool, `submit_job_extract` — no browser** (since 2026-09-24). Pointing `MODEL_NAME_EXTRACTOR` at an `ANTHROPIC_*` const selects the agentic SDK session, which still browses for itself
  - includes: Read Job Page
  - includes: Detect Posting Language
- **Detect Posting Language**: capture `posting_language` — the language the **source page** is written in. It must be judged from the original page, **never** from the extractor's own output: the extractor translates as it condenses, so a French posting comes back as English prose with only the title left in French (2026-08-13: a French Valtech posting came back as English prose and was rated 4/5 and notified). There is deliberately **no** code-side heuristic over the posting's *prose* — guessing a language from condensed text is exactly the mistake this field exists to avoid, so `posting_language` has no `derive_` fallback and is the one language fact the extractor still supplies. It drives Cap Foreign-Language Rating and a deterministic warning; it never rejects. Invoked by Extract Job Posting
- **Detect Likely Working Language**: resolve `likely_working_language` — the language a professional, office-based team at the job's **location** most likely works in day to day — from Classify Job Location alone, via `derive_likely_working_language()`. **It asks for the working language, not the national one, judged at the most specific place named** (2026-09-29): the field was `implied_local_language`, asked as "the dominant working language of the FIRST country", and it notified `Luxembourgish` for a Luxembourg work-from-anywhere role while answering every Montreal and Québec location `english`. The rename is also the cache invalidation — an entry without the new field is a miss and is re-asked, and the stale fallback serves the old answer only when the re-ask fails. **What the posting says beats what the place implies**: when the JD states a working language (`stated_working_language`) or a required one (`language_requirement`), the location's guess is neither warned nor shown to the rater; a stated language the User does not speak gets its own `Working language: … (stated in posting)` bullet, and a required one the User lacks is already a hard rejection. **A remote role across a multi-country area** (`residency_scope` `area_wide`, or the classifier's `broad_area`) gets the location's language as a **marginal** warning — the office's language is then one of many, not where the holder works. **The extractor is not asked and cannot override it.** A place implies a language (Italy implies Italian); that is reusable world knowledge about a location, so the cache is what makes it deterministic — two Berlin jobs cannot be answered differently, within a run or across runs. This deliberately reverses the earlier design in which the extractor supplied the field and its *foreign* finding beat the classifier's. That rule bought one thing — a language named only in the posting body, like Valtech's "colleagues outside Quebec" on a `Canada (Remote)` posting — at the price of a fact about a place being re-decided per job; such a body-only signal is no longer detected, and the Valtech posting's outcome is unchanged because `posting_language` still caps it. **It gates nothing and caps nothing** — it warns, and the geographic rule deliberately does not read it. Invoked by Evaluate Job Fit
- **Apply Hard Rules**: force rating to 1 if the Job Posting is closed ("No longer accepting applications"), older than `JOB_STALE_AGE_DAYS`, located where the user needs sponsorship but none is offered, explicitly requires a language the user does not have, hard-requires a degree the user does not hold, is **anchored in a place on `would_not_live_here`**, or **states a required relocation to one**. Every rule but the blacklist and the geographic pair is deterministic and $0; all but closed/stale read their thresholds from Preferences and are inactive when unconfigured. The stale rule needs a parseable posting date, and an unparseable one switches it off for that job with only a WARNING. `parse_posting_date()` therefore accepts a leading `YYYY-MM-DD`, or else an `N minutes/hours/days/weeks/months ago` anywhere in the string. That covers forms like "Reposted 4 days ago" and "Posted 19 hours ago (viewed …)", which produced 98 warnings across logged runs before 2026-09-24. A date after the relative phrase is treated as the viewing date, never as the posting date. Every rejection is logged with its reason

- **Reject Blacklisted Company**: force rating to 1 when the Job Posting's poster **or** its `end_client` is on the user's Preferences blacklist. Runs **first** among the hard rules — it is the most decisive and costs nothing when the name does not match. The trigger is an **exact, case-sensitive** name match (`company_blacklist_reason()`), deliberately *not* the normalized fuzzy `company_matches_applied()` path: a standing user-authored blacklist must never over-block. A name hit then costs **one** cheap LLM confirmation call, because an exact name string can collide across organizations ("Cohere" the AI lab is not Cohere Health); a confirmed collision does not reject. The confirmation call sees the posting's description, budgeted to `BLACKLIST_CONTEXT_DESCRIPTION_MAX_CHARS` **only after the name hit**. Budgeting it up front logged a truncation for every job on every run, for text nothing then read (20 on 2026-09-24). **Any failure of that call rejects anyway** — the name matched, and a tool-server outage must not quietly readmit a blacklisted company. The end client is checked for the same reason Deduplicate by End Client exists: a recruiter reposting the role would otherwise get around it. Preference-driven and inactive when the list is empty. - **Classify Job Location**: resolve a location string into geographic facts — the countries named, one region per country (`southern_europe` / `northern_europe` / `western_europe` / `eastern_europe` / `north_america` / `other` / `unknown`), a `broad_area` flag, the local working language, and **`place_names`** — every other name those places go by, English and local, properly cased and accented — via one cheap LLM call **cached in `run_dir/location_cache.yaml`** by normalized location string. Only reached for a location the exempt lists do not name, so in steady state it is a cache hit or never called. **This does not violate "a structural fact must never be left to a model's discretion"**, and the distinction matters enough to state: the model answers a question about a *place*, never about the job — reusable world knowledge, checkable by a human, identical for every job in that location — while the **cache** is what makes it deterministic (two Berlin jobs cannot get different answers, within a run or across runs) and the **policy stays in code** (a country is rejected by a deterministic read of the user's `would_not_live_here` list). The regions are recorded and shown, but **decide nothing** — see below. Same shape as `company_blacklist_reason()`, which matches a user-authored list deterministically and spends one cheap confirmation call only on the ambiguous case. **`place_names` deliberately does not ask "does this match the user's list"** — that question depends on the list, so its answer would go stale on every list edit, whereas a question about the place alone is cached by the place alone and stays true forever. A cached entry predating the field is treated as a miss and reclassified: serving it would silently disable alias matching for that location, which is the same shape as the dead `malaga` entry the field exists to fix. **`countries` come back as proper names too**, like `place_names` and unlike `regions` and `likely_working_language` — those are enum vocabularies with no correct written form, a country is a place. So the constant naming EU membership (`location.EU_MEMBER_STATES`) is written `Austria`, `Czechia`, and `is_eu_member()` folds at the comparison against a **derived** index rather than storing a second, folded copy of the list: a constant holds the real name of the thing it names, code folds where it must, and a name folded into the data can never be unfolded. Pinned by `test_eu_constants_are_written_as_proper_names`. **Fails open** — see Resilience.

  **Measured limitation, and why regions no longer decide anything.** The cache guarantees a given location *string* is always answered the same way; it does **not** guarantee two strings naming the same country agree. Measured 2026-09-04: `Dublin, Ireland` → `western_europe` but bare `Ireland (Remote)` → `northern_europe`, and the same split for `London, United Kingdom` vs `United Kingdom`; later the live cache held 5 of 40 countries in two regions at once. That is why the region rule (`reject_regions`, briefly `would_not_live_in_regions`) was removed: **a country is decided by name, on `would_live_here` / `would_not_live_here`** — plain string matches that no classifier variance can reach.

  Verified against real postings by `scripts/backtest_location_gate.py`; re-run it whenever the classifier model or the gate's rules change. The first live run justified the classifier over the hand-written country table it replaced: under the region policy of the time it split `Aix-en-Provence → southern_europe` (keep) from `Hauts-de-France → western_europe` (reject) with no city list at all
- **Reject Excluded Location**: force rating to 1 when the Job Posting's `location` is anchored in a place on `locations.would_not_live_here`, or its `relocation` field states a required move to one. **Purely geographic — it reads no language field, and must never be changed to.** An earlier draft rejected on "non-English AND not on the acceptable list", which produces the right answers for Spain and Germany for the wrong reason and the *wrong* answer for a French-language remote role in Canada (the exempt list named Vancouver and British Columbia, not Canada). What language a place speaks is `likely_working_language`, it warns only, and folding it back in here reintroduces that bug.

  **The gate is three lists and a guess**, resolved by `rejected_location()` in this order:
  1. **Inert** unless `would_live_here` or `would_not_live_here` is non-empty — not one classifier call otherwise. `would_commute_here` on its own configures only the cap.
  2. **Exempt**: the location matches `would_live_here` ∪ `would_commute_here` (commuting somewhere implies being there) → keep. So `France` can sit on the deny list while Toulouse and Nice, listed as exempt, still pass.
  3. **Classify** the location (cached, see Classify Job Location) and re-check the exempt lists against its `place_names`.
  4. **`broad_area`** → keep. A posting offering a whole multi-country area is not limited to the countries it happens to mention, so `European Union (Remote, UK and EU)` passes though the UK is its only named country — a real 5/5 posting of that shape was flipped by the first live backtest. A single anchored country phrased expansively is **not** a broad area: `Berlin, Germany (Remote across Europe)` is not `broad_area` — it is kept by step 5 instead, as `residency_scope: area_wide`. Both directions are pinned, because a `broad_area` creeping toward true silently disables the gate.
  5. **Residency spare** (`residency_spare()`). **A bare location is not a residency requirement** — "Germany (Remote)" anchors the role in Germany while the holder could live anywhere in the EU. For a `remote` posting: `area_wide` ("anywhere in the EU", "Work from Anywhere") → keep; unspecified → keep **iff every country named is an EU member state** (`location.EU_MEMBER_STATES`), because an EU anchor implies work rights the user has and a UK, Serbian, Norwegian or Swiss one does not; `country_only` ("Remote within country", "must be based in X") → no spare. `hybrid`/`onsite` never get a spare: an office pins you to the office, which is the Munich/Berlin case this gate was built for.
  6. **Deny**: reject only when **every** country named is on `would_not_live_here`, matched against the country and, when only one is named, its `place_names` (so `Praha, Czech Republic` is denied by an entry `Czechia`). "Spain or the Netherlands" leaves somewhere to be. A location naming no country is rejected only on a literal list match (`Blockedland (Remote)`).
  7. **Guess**: any named country none of the lists names is queued for Guess Unbucketed Location, and the posting is **kept**.

  **The deny list is deliberately evaluated after the spares.** `would_not_live_here` says where the user will not *live*, so it bites when the job actually pins residence there (`country_only`, hybrid, on-site) and not when a silent EU anchor means they would live elsewhere in the EU — a silent `Poland (Remote)` is kept even with Poland on the list; pinned by `test_would_not_live_here_applies_only_when_residence_is_pinned`. **The `relocation` half is never spared**: it goes through the same function with no residency spare, because a stated relocation is the JD asserting a requirement outright (`test_relocation_rule_is_unaffected_by_the_eu_remote_spare`). `would_not_live_in_regions` is **gone**: a country used to be decided by whichever region the classifier assigned it, and 5 of 40 countries in the live cache sat in two regions at once.

  **Every list match is whole-word, case-sensitive and accent-exact, against place names written the way places are written.** Lowercasing the lists is what made `malaga` an entry that could never match `Málaga` while looking exactly like one that had merely not come up yet. Case-sensitivity and the boundary class had to change **together**: `(?<![a-z0-9])` blocks only lowercase ASCII neighbours, so matching proper names with it lets `ROMA` reach into `ROMANIA` and `Roma` into `Romaña` — the original bug in caps and via an accent. The class is `(?<![^\W_])` (unicode letters and digits) and there is deliberately no `re.IGNORECASE`, because `Nice` the city is not `nice` the adjective. **Step 3 catches what exact matching cannot**: once the classifier returns, the lists are re-checked against its `place_names`, which is how a posting saying `Torino` matches a list saying `Turin`, and `München` matches `Munich`. Exonyms are unreachable by any normalization, and hand-maintaining spelling pairs is what introduced `roma` in the first place. Resolved once per candidate into `extract['place_names']` and written back, so the three sync consumers (`commute_location_is_acceptable`, `apply_rating_caps`, `build_deterministic_warnings`) agree with the async gate instead of a hybrid role in `Sevilla` being gated correctly and still capped. **`sponsorship_required_in` is the one list still on case-insensitive substring matching** — a separate rule whose match direction is inverted, left alone rather than widening this change. The exempt list (then `hybrid.acceptable_locations`) contained `roma` (Rome) and `'roma' in 'romania (remote within country)'` is `True`, so tier 1 exempted **every** Romanian posting before the deny list, the classifier and the region policy of the day were ever consulted. The boundary must be a lookaround on the token's own edge characters, **never** `\b…\b`: `re.escape('u.s.')` is `u\.s\.` and `\bu\.s\.\b` matches nothing at all, so the obvious fix silently deletes a real entry. Counted as `hard_ruled_location` / `hard_ruled_relocation`; invoked by Apply Hard Rules
  - includes: Guess Unbucketed Location
- **Detect Residency Scope**: capture `residency_scope` — whether the JD explicitly pins residence to the country the role is anchored in (`country_only`), explicitly offers a whole multi-country area (`area_wide`), or says nothing (empty) — on the **existing Stage 2a extract call**, with `derive_residency_scope()` as a deterministic fallback. **The precedence is asymmetric and load-bearing**: a `country_only` finding from *either* source wins, and is tested first — the union direction, because only the *permissive* value can silently switch a gate off. A wrong `area_wide` **silently disables the geographic gate** for that job — the same failure `broad_area` is pinned against in both directions — while a wrong `country_only` surfaces as a rejection with a stated reason in the audit log and the funnel. Between the two *permissive* values the extractor wins (the `is_agency` shape), since it read the body and the regex is a backstop. The fallback patterns are anchored on a **concrete non-area object**, which is the whole trick: "must be based in Germany" pins you and "must be based in Europe" does not, and they are the same words up to the last one. Every branch naming Europe uses the one `_EUROPE_WORDS` constant (`EU`, `E.U.`, `EEA`, `EMEA`, `Europe`, `European`), so "EEA or US" and "EMEA/EU" read `area_wide` exactly as "EU or US" and "EU/Europe" do; `US`/`USA` alone are deliberately **not** area words, so "must be based in the US" stays `country_only`. - **Guess Unbucketed Location**: at the end of Stage 2, for each country the gate met that none of `would_live_here`, `would_not_live_here` or `not_yet_bucketed` names, make one cheap LLM call (`resolve_location_guesses()`) asking which list it resembles, **judging only by the pattern of those two lists** — the prompt is not given `relocation_note`, which once argued a model into overriding the lists (see "An advisory reviewer must not be able to argue with the config it reviews"). - **Review Country Lists**: once per non-interactive run, run two **deterministic, free** hygiene checks over the user's place lists (`would_live_here`, `would_not_live_here`, `would_commute_here`) against the places actually seen this run — accumulated in `location.py` on **both** the cache-hit and LLM paths, since in steady state almost every location is a hit and an LLM-only accumulator would report a country once and never again — and record findings as `entry_warnings` in `run_dir/location_recommendations.yaml`. **It never edits a preference and makes no LLM call**: the judgement half ("would they live in this country?") moved to Guess Unbucketed Location, because asking one question in two places is two sources of truth for one decision. **Substring collisions**: an entry that sits inside another place — `'Roma' ⊂ 'Romania'` is arithmetic, "a structural fact must never be left to a model's discretion" applies to the reviewer as much as to the rater, and it keeps working with the tool server down. That folded comparison is **whole-token, never a substring**: folded `roma` sits inside folded `romania`, so a substring form would advise rewriting the entry as `Romania` — advice to reintroduce the very bug. Folding may ignore case and accents; it may never ignore boundaries. The two language warnings are independent: a French JD gets the first (plus the cap), an English JD in Montreal or Madrid gets only the second — unless the JD itself states the working language, or the role is remote across a multi-country area (then marginal); see Detect Likely Working Language. The rater cannot be trusted to self-report any of these: it once saw "Hybrid - 2-3 days onsite" and rated the job 4/5 without warning, it rated the French-language Valtech posting 4/5 and notified it with no language warning at all, and on the 2026-08-11 run it volunteered the agency fact for CyberCoders and Jobgether but not for Hire Feed or Genius Innovation Lab — 2 of the 4 agency postings that triggered a notification said nothing. What moved into code on 2026-09-22 is whether the posting states a *complete range*, which is a property of the string and needs no Preference. **Salary-vs-target is decided in code only where it is a plain bound comparison, and left to the LLM everywhere else** (2026-09-23): **a complete range is on target when its upper bound reaches the Preferences `compensation.base_target`** — the band is negotiable, so its floor and midpoint are not a concern — and a fifth line, `Salary below target — whole range under …`, is emitted only when the upper bound falls short. Code decides only a single two-ended **annual** range quoted in the target's own ISO currency (`salary_meets_target()`); a bare `$`, another currency, an hourly or day rate, a string stating several ranges (per region or tier — the Salary Reading keeps only the first), and a range that bundles bonus or variable pay (OTE, "combined", "total cash compensation" — not comparable with a *base* target) all stay with the rater, since converting them is too brittle for a rule. That still holds after Convert Salary Currency (2026-10-08): the conversion is shown beside the posting's figure and feeds nothing — `salary_meets_target()` still abstains on another currency. When code decides the range is on target, the rater's extract says so (`Salary vs target:`), and every rater salary bullet is dropped at merge. The rater's midpoint and lower-half reasoning was the incident: for job 4470446597 (`CA$170,000 - CA$240,000 per year`) it warned "Base target … sits in upper half of range; lower bound well below target" about a range the User considers on target; replaying the saved corpus found 18 such bullets on ranges whose top cleared the target, and none carrying anything else. The evaluator prompt carries the same upper-bound rule for the cases code leaves to it. **An incomplete range warns, and so does a below-target one; neither caps the rating.** A stated floor is real information, capping would have withheld the very notification that exposed the partial-range problem, and JOB_REQUIREMENTS accepts below-target pay when other factors are strong
- **Classify Salary**: resolve a Job Posting's free-text `salary` into a Salary Reading. **Rules first**: eight ordered tiers (empty; a no-figure vocabulary such as "competitive"/"not specified"; a two-ended range; a floor marker; a ceiling marker; a lone monetary amount; anything else) answer 862 of the 911 figured strings in the saved corpus for free, and a deterministic check is never truncated. Only a string **no rule could read** reaches one cheap LLM call, cached in `run_dir/salary_cache.yaml` by normalized text, so a phrase is parsed once ever. **This does not violate "a structural fact must never be left to a model's discretion"**, for the same three reasons as Classify Job Location: the model answers a question about a *string* ("what amounts does this phrase state?"), never about the job or the fit; the **cache** is what makes it deterministic; and the **policy stays in code** — which readings warn is a table in `agent._SALARY_WARNING_BY_KIND`. **Fails toward saying less**: a provider outage, or a model that labels something a `range` without two numbers, yields `unclassified`, never a silent upgrade of a partial range to a complete one. Invoked by Evaluate Job Fit; included by Build Deterministic Warnings
- **Retain Raw Posting Text**: write the Raw Posting Capture — the JS-free page archive first, then the text the extractor reads — on every path through Read Job Page. Pruned at the start of each non-interactive run. Deletion is narrow on purpose — only a direct child of `raw_postings/` whose name parses as a date past the window, with containment re-checked after resolving the path, and anything else left alone and reported; this is the only code in the repo that deletes the User's data. Extends Extract Job Posting
- **Check Salary Provenance**: compare every amount in the extracted `salary` against the amounts in the Raw Posting Capture, as **numbers** rather than digit strings (a page writing `CA$208,580.00/yr` and an extract writing `CA$208,580` state the same number). A mismatch logs a WARNING and marks the Salary Reading's `source` as `unverified`; it never rejects, because a capture that missed the compensation block is at least as likely as a model inventing a figure. This is the first implemented slice of the provenance validation the Anti-fabrication requirement has carried as designed-but-unimplemented — `submit_job_extract` is generative, and until the page was retained there was nothing to check a figure against. Extends Evaluate Job Fit
- **Convert Salary Currency**: for a Saved Job at the notification threshold, compute the Salary Conversion — the Salary Reading's bounds in the Preferences `compensation.convert_to` currency, at the Exchange Rate Service's daily rate — and show it after the posting's own text, marked `≈`. **The posting's text is never replaced.** Rates are fetched at most once a day and once per run (`fx.rates_for`), cached in `run_dir/fx_rates_cache.yaml`; a failed fetch serves a table no older than `FX_RATES_STALE_MAX_DAYS`, and past that shows nothing. **Shows nothing rather than guess**: no conversion for a currency in `compensation.keep_currencies`, an unresolved currency (a bare `$` or `kr`), a string stating several ranges or naming several currencies (the reading holds only the first), an `unverified` reading, or a currency with no published rate. The pay period is kept as written — an hourly rate converts to an hourly rate — and the result is rounded to `SALARY_CONVERSION_SIGNIFICANT_FIGURES`. Display only: no rating, cap, gate or warning reads it. The Saved Job records the rate and its date. Extends Notify User of Match
- **Estimate Pay Range**: for a Saved Job at the notification threshold whose Salary Reading is `absent`, ask `MODEL_NAME_SALARY_ESTIMATE` for the base pay range such a role typically offers, in the job market's own currency, from the title, company, location and the full page text (the condensed description on the Anthropic extract path, which retains no page); capped by `SALARY_ESTIMATE_TEXT_MAX_CHARS`, cut from the middle and reported. **Only `absent`**: a partial or unreadable figure is the posting's own and is never estimated over. "Cannot estimate" is a first-class answer, and code drops any answer that does not validate — one-ended, inverted, wider than `SALARY_ESTIMATE_MAX_SPREAD_RATIO`, or outside the closed currency and period vocabularies. Cached per job in `run_dir/salary_estimate_cache.yaml`; a provider failure shows nothing and caches nothing. Shown on the `💰` line as `Not listed — model estimate:`, then passed through Convert Salary Currency; the Saved Job also records the model and its stated basis, which stay out of the Telegram message because they are model free text. **It runs after rating and is kept out of the extract text, so it cannot reach the rater**; `No salary listed` is still emitted and the rater's own salary bullet is merged as before, so a message can carry two model opinions on pay. `SALARY_ESTIMATE_ENABLED` switches it off. Extends Notify User of Match; includes Convert Salary Currency
- **Flag Agency Posting**: capture whether a scraped Job Posting's poster is a staffing firm, recruiting agency, or job aggregator rather than the hiring employer, plus the `end_client` when the posting names one. Captured as structured `is_agency` / `end_client` fields on the **existing Stage 2a extract call** (no extra LLM call), with `derive_agency_posting()` as a deterministic fallback used **only** when the extractor leaves `is_agency` unset — the extractor's `False` is a judgement and wins. The fallback is intentionally weak (phrase-level "our client is…", agency markers in the poster's name): measured against the 2026-08-11 corpus it caught 1 of 10 agency postings on its own, while the extractor field classified 15 of 16 correctly, so the LLM field is the real mechanism and the regex is a backstop. `derive_end_client()` discards an end client equal to the poster — extractors routinely echo the company back (measured: `end_client='lululemon'` on a lululemon posting). **Agency status never rejects and never changes the rating.** It warns, and it is the gate on Suppress Recruiter Repost — the one thing it decides is whether a *repeat* notification for a role already sent goes out; extends Evaluate Job Fit
- **Deduplicate by End Client**: when a scraped Job Posting names an `end_client`, match **that** against the already-applied blocklist (`company_matches_applied`), because Stage 1b matched the agency's name and so misses a recruiter reposting a role at a company already applied to directly. Counted in the funnel as `end_client_already_applied`. Deliberately **not** extended to the agency's own name (see the Recruiters note above) and deliberately **not** used to dedupe the same role across different posters. The *same* poster re-advertising one role is a different problem and is handled by Suppress Recruiter Repost
- **Suppress Recruiter Repost**: when an agency posting is about to be notified, withhold the message if the same agency already had a posting of **the same role** notified within `RECRUITER_REPOST_WINDOW_DAYS`. The rating, the Saved Job and the audit entry are unchanged; only the Telegram message is withheld, and the Saved Job carries a code-built "Likely repost of job `<job_id>`" warning naming the earlier posting, since a notification that never arrives is otherwise invisible. Two steps: a **free deterministic gate** (same `agency_key` — `_normalize_company()` of the poster — inside the window; no prior means **no LLM call**, which is essentially every job), then **one cheap call** that judges sameness. **A different country, day rate, or title wording does not make it a different role**; a different client or programme does. The model may only return a `job_id` **from the list it was shown**, and one outside that list is treated as no match. **Fails open** — any error notifies. Only *notified* postings are recorded, so a role first rated 3 still notifies when a repost rates 4; and a suppressed repost is **not** recorded, so the original stays the reference point and a role still being advertised after the window notifies again. Counted in the funnel as `recruiter_repost_suppressed`, with the job outcome `recruiter_repost`; extends Notify User of Match

  **Why text similarity is not used, measured 2026-09-10.** Archer Recruitment advertised one pharma programme under 6+ job ids in nine days — a different country and day rate each time — and every one rated 4-5 and notified. `(site, job_id)` dedup cannot see a new id, and the already-applied blocklist deliberately never holds agency names. But the extract **is a rewrite**: the extractor condenses (and translates) in its own words, so word-shingle containment across those six postings ran 0.62-0.86 for three of them and **~0.0** for the other three, while unrelated repostings by direct employers (Datadog, Pipedrive) scored 0.7+. No threshold separates them. Embeddings were not measured and are not obviously better: every posting a recruiter surfaces here is an agentic-AI role, so they cluster regardless of whether the hiring organization is the same.

  **The dangerous error is the false MATCH, and the first prompt made one.** Replayed over the real corpus on 2026-09-11 the check was right about Archer — it matched the Sep 10 Portugal posting to its Sep 09 sibling, citing the identical day rate and the same recruiter's contact address, "just re-posted with 'European Union' changed to 'Portugal'" — and wrong about **Jobgether**, an aggregator: it called "Senior Software Engineer, AI Automation" the same role as "Staff AI Engineer (Data & Intelligence function)", reasoning from **adjacent job ids** and the shared agency. Neither is evidence, and unlike a missed match, which costs one duplicate ping, a false match **hides a real job**. So the prompt names the non-evidence outright (same agency, adjacent ids, shared seniority, both being remote AI roles), tells the model to judge on the body — responsibilities, requirements, the client, a rate, a contact address — and says to answer empty when unsure. The asymmetry is stated in the prompt itself rather than left implicit, and `test_repost_prompt_says_what_is_not_evidence_and_which_way_to_err` pins it. **An agency running one programme and an aggregator posting for fifty clients are not the same problem**, and a check tuned on the first will over-match the second

## Non-functional Requirements

- **A structural fact is decided in code, never left to a model's discretion** — a model that can see a rule still applies it differently each time the fact comes up. The rater capped a Munich role for relocation in its prose and left identical Berlin and Stuttgart roles at 5 (2026-09-04); it rated a hybrid role 4/5 while naming the hybrid location as a drawback, and a French posting 4/5 with no language warning (2026-08-13); the scraper diagnosed its own dead region filter six times in the run log and nothing acted on it (2026-08-18). So gates, caps, warnings and health alerts live in code: the model reports what it observed through a tool, and `evaluate_ui_contract`, `apply_rating_caps`, `build_deterministic_warnings` and `assess_run_health` decide. An LLM call inside a rule is acceptable only when it answers a question about the world rather than the job, is cached so the answer is deterministic, and leaves the policy in code. The location classifier and the blacklist confirmation call are the two precedents. **Suppress Recruiter Repost is the third, and it is the one that bends the rule**, so it is stated plainly rather than buried: its question is about the *job*, not the world, and it is not cached. It is allowed because it is a question of organizational **identity** ("is this the same position at the same hiring organization?"), the same shape as the blacklist confirmation; because the policy — the window, who is compared, what a match does — stays in code; because a job is evaluated once ever, so the verdict is asked once and written into the Saved Job and the audit log where a person can check it; and above all because **it changes no rating and rejects nothing**. A wrong answer costs one duplicate Telegram message, or one that arrives a few days later than it might have. Do not extend it to anything that gates a rating (2026-09-10). **Estimate Pay Range is a fourth LLM call, and it sits outside this rule rather than bending it** (2026-10-08): its question is about the job and its answer is a judgement, so it could never qualify — and it does not need to, because it is inside no rule. It runs after the rating, reaches no gate, cap or warning, and is shown labelled as the model's estimate. The moment anything reads it to decide something, this requirement applies and forbids it
- **Anti-fabrication (the model chooses ACTIONS; code moves DATA)** — a tool argument must be a **decision**, never a payload code could have read itself. An LLM has no mechanism separating "I am copying this" from "I am producing this": both are token generation conditioned on context. So when the data is not in context — a call errored, a result was truncated, diverted to a file, or scrolled out — it does not fail, it emits the most plausible continuation, which is a well-formed, schema-valid object. **There is no failure mode where a courier notices it lacks the data**; absence produces fiction, and the fiction passes shape validation because shape was never the problem. Measured 2026-08-21: the model passed `filename` to `browser_evaluate`, the result went to disk, and it then invented an entire page report for `report_search`. Code caught it (`UI CONTRACT FAILED`) only because judgement already lived in code. **Test any signature by asking: if the model had never seen the data, could it still fill this argument plausibly?** If yes it is a *courier argument* — delete it and let code fetch the data. Diagnostic: **"verbatim" / "exactly as returned" / "do not summarise" in a tool description is a courier argument confessing itself**, and the instruction is unenforceable. This cannot be fixed by prompting — "never invent a report" competes with the drive to produce a plausible completion and loses precisely when data is missing; removing the argument removes the *opportunity*, which is not probabilistic. Stage 1b's toolset (`run_ui_contract`, `harvest_listings`, `record_listings`, `report_problem`) therefore accepts only `region` and `what_happened`; the harvest is held in `ScrapeSession` and handed to `do_record_listings` directly, `filename` is stripped from **every** browser tool call and each drop is logged as a WARNING (2026-10-01: the strip named two tools, the scraper's schemas come from the live server, and an `@playwright/mcp` release added `filename` to `browser_find`, which would have reached the model with no change here; `browser_console_messages` had been exposed the same way all along), and **"I don't know" is a first-class, rewarded outcome** (`report_problem`) because the model fabricated partly for lack of any way to say so. Unit tests pin all of it, including one that calls `record_listings` *with* fabricated job data and asserts the fabrication is ignored. **A required parameter the model cannot observe is fabrication pressure, not validation.** The SDK's `{"name": str}` shorthand marks every param required (`claude_agent_sdk/__init__.py:422`), which silently made `date_posted`, `url`, `content`, `query` and `job_id` mandatory on tools whose descriptions call them optional. A model that cannot see a posting's date must then either refuse the call or invent one — and refusing is the behaviour that is *not* guaranteed. Declare optional params with the full JSON Schema form and a correct `required` list; `test_optional_tool_params_are_not_declared_required` pins the three tools involved. **Stage 2a's `submit_job_extract` is generative and cannot lose its courier role** — it needs provenance validation instead (`job_id` present in the navigated URL, title/company as normalized substrings of a re-fetched snapshot, enums restricted to the allowed set, falling back to `extract_job_page_direct()` on mismatch); designed, **not yet implemented**. **Stage 2 reads the page in code** (2026-09-24): the URL, the render wait and the page text are data code already has, so the extractor model is handed the text rather than choosing what to read — and the page is de-cluttered first, because a model reading "More jobs" can copy another company's salary into this job's `salary` field
- **Scraper tool surface** — Stage 1b restricts the Playwright toolset via `disallowed_tools` (`SCRAPER_DISALLOWED_BROWSER_TOOLS`), which is the only option that removes a tool from the model's context. `allowed_tools` does **not** do this: it only auto-grants permission, which `permission_mode='bypassPermissions'` already grants, making it inert — measured, the model saw all 24 Playwright tools with `allowed_tools` set to 4. `browser_evaluate` and `browser_click` are load-bearing for discovery (inner-container scroll lazy-loads 7 → 10 listings; Next yields a fresh page) and a unit test asserts they are never disallowed
- **Cost efficiency** — **The scraper's provider is chosen by code, once per run, on effective price** (2026-09-24). Under the tool server's bpw pin, OpenRouter spread each scraper conversation across ~16 fp8 providers weighted by prompt price, then kept it on the first for the cache. Token volume was steady at ~20M per run, 94% of it cache reads, and those providers' cache-read prices differed ~40x — so identical runs cost $0.05 (2026-09-23) or $1.59 (2026-09-24), and a week of unlucky draws cost ~$5-7 with nothing flagging it. Rank endpoints by the price of the actual token mix, never by prompt price alone: the cheapest prompt price can be the dearest endpoint once cache reads dominate. See Pin Scraper Provider. **The Anthropic scraper fallback is capped per run at `SCRAPER_ANTHROPIC_FALLBACK_MAX_COST_USD`** (2026-09-29): it bills Haiku prices on the same cache-heavy traffic, and on 2026-09-28 it was ~$4.96 of a $5.30 run. Past the cap the remaining queries are skipped and marked as errors, with a `scrape_budget` alert, and a `provider_fallback` alert is raised whenever the fallback runs at all: a thinner run is preferable to a silent multi-dollar one. Moving the other stages to a local model was weighed and rejected the same day, since together they cost ~$0.015 per run. Haiku for scraping, page extraction, and applied-job metadata; the agentic browser work never runs on Sonnet. Query generation is the one deliberate exception: a single Sonnet call per run (~$0.33), because top-of-funnel query relevance is the pipeline bottleneck and everything downstream is gated by it. Applied-job metadata is cached in `index.yaml` by mtime, so the extraction cost is paid once per PDF. Hard rules and local triage reject clear non-fits for $0 before any paid rating call. **A triage gate that has silently stopped running still looks free — it just stops saving anything**, which is what Preflight Local Model exists to make visible. The triage model is sized to the job (one 1-5 JSON score): `OLLAMA_MODEL_NAME_TRIAGE`, not the 30B tier, measured to track the strong rater with zero false 1s across ratings 1-5. The company blacklist is the one hard rule that can cost anything, and only on an exact name hit — a non-matching name short-circuits before any call, so the gate is free on essentially every posting; do **not** "optimise" this by dropping the confirmation call, which is what stops a same-named organization being rejected by mistake. Since LinkedIn no longer enforces `f_E` server-side, a $0 title check at queue time (`title_rejection_reason()`) keeps below-seniority and people-management listings out of the paid Stage 2 path, where each would cost an extract plus a rating call; it is deliberately conservative (word-boundary matches only, and neither `associate` nor bare `graduate` rejects) because an auto-skip is unappealable, and it never filters on work arrangement, which is unreliable on a search card. The rating call is a single non-agentic structured-output call (route and model pinned explicitly by `MODEL_NAME_RATING`, never the CLI default model). **No output-token ceiling is sent anywhere**, deliberately: `LLM_JSON_MAX_TOKENS = 3000` was inherited as a default argument by all eight call sites rather than chosen by any, against models allowing 131,072 completion tokens with no server-side clamp, and every one of the 13 truncations across 2026-09-01..03 was `completion_tokens: 3000` exactly and survived a model change. Removing it *lowers* cost: a truncated company-match paid for 3000 reasoning tokens, returned `null`, and then paid again for the Anthropic fallback — finishing the answer is cheaper than paying for both halves of a failure. If a ceiling is ever genuinely needed, pass `max_tokens` at the call site that needs it. Guess Unbucketed Location adds one cheap call per newly seen undecided country and normally **zero** — a country is asked about once, ever — and Review Country Lists is deterministic code that costs nothing and keeps working when the tool server does not. The geographic gate is free on essentially every posting — two user-authored list checks, then a **cached** classification per distinct location string — and it runs before the rating call, so a rejected job costs no rating. Reference jobs are distilled once into a cached profile of at most `REFERENCE_SUMMARY_MAX_CHARS` instead of a block of up to `MAX_REFERENCE_JOBS` × `REFERENCE_JOB_PROMPT_MAX_CHARS`; the evaluator prompt is built once per run and reused across all jobs to maximise prompt-cache hits; the extractor is capped at `EXTRACTOR_OPENROUTER_MAX_ITERATIONS` (`EXTRACT_FALLBACK_MAX_TURNS` on the Anthropic fallback) and restricted to the browser tools it needs. **Account safety still outranks cost in Stage 1b**, and its prompt stays deliberately verbose — but cost there is no longer unmanaged: it reached **86.9% of total run cost** ($48.24 of $55.52 over ten runs, peaking at $10.06), so it moved to `MODEL_NAME_SCRAPER` (`OPENROUTER_MODEL_NAME_SCRAPER`), measured 9.3x cheaper on identical traffic. Pacing was **not** traded away: the randomised delays are unchanged. Do not optimise Stage 1b for speed or turn count; optimise **what enters the model's context**, and **which model reads it**. Two mechanisms did most of the work, both measured rather than assumed: a fresh conversation per query (the shared Anthropic transcript grew context per turn 41K → 162K across a run), and batching a search's recording into one `do_record_listings` call instead of ~25 per-listing turns — which also removed 69% of output tokens, since the model no longer re-emits job objects. **Every `ClaudeAgentOptions` site in the package must pass `setting_sources=[]`, `strict_mcp_config=True` and `skills=[]`** — unset, they load CLAUDE.md in full plus every global MCP server into even a one-word classification call. This was fixed in `agent.py` on 2026-08-21 and the four sites in `tools_generic.py` were missed for three months because the note said "in `agent.py`" (measured 2026-08-24: **22,945 → 294 tokens, 78x**, on the PDF categorization options). Prose cannot enforce this, so `test_every_claude_agent_options_site_limits_context` walks the AST of every module in the package and fails on any site missing them The original leak measurement was 45,523 tokens → 358 on a bare options object once the three flags were set. Of that, 31,384 tokens were CLAUDE.md itself and 13,781 were nine unrelated global MCP servers, re-read on every turn (2026-08-21). **Every Playwright action tool auto-snapshots the page.** In the pinned bundle, 18 action tools call `setIncludeSnapshot()`, which resolves to `"full"`, and `browser_wait_for` is one of them. So each randomised safety pause also bought an ~8K-token snapshot: ~1.92M tokens of cache-write across 12 searches, against 1.96M measured. `--snapshot-mode none` would fix that without affecting an explicit `browser_snapshot`. It is **not yet applied**. When choosing `MODEL_NAME_SCRAPER`, compare cache-read prices, not list prices: five of eleven candidates cost more than Haiku on this traffic. The triage model was sized against 17 saved postings spanning ratings 1-5, with zero false 1s, and it erred high where it disagreed. Re-run that comparison before swapping this model again. A false 1 costs a real job, because a triaged-out job is never rated (2026-08-25). The recruiter-repost check follows the blacklist's shape: free unless a **free** deterministic gate matches first (same agency notified inside the window), and it only runs at all for an agency posting that is about to be notified — so `recruiter_repost` reads $0.0000 on a run where no agency posted twice, which is most of them
- **Observability** — the generated Search Queries are logged; every `check_and_record_job` outcome is logged (`new`/`already_processed`/`already_applied`/`too_old`/`auth_required`) so seen-but-deduped is distinguishable from never-seen; per-job logs of the extract signal (`date_posted`/`location`/`closed`/`language_requirement`/`posting_language`/`likely_working_language`/`relocation`/**`residency_scope`, raw and derived**/`education_requirement`/`is_agency`/`end_client`), extract compression, hard-rule short-circuits, triage score vs. final rating, and the rating model used. Blacklist activity is logged in three distinct forms so each is separable: a confirmed rejection, a **name collision** the confirmation call cleared (a blacklist entry matching a different organization by name), and a confirmation **failure that rejected anyway**; expired and undated entries warn once per run. Each run emits a single `Run funnel: {...}` line (queries → listings seen → check-status counts → candidates → extract ok/failed → hard-ruled by reason, including `hard_ruled_blacklisted` → triaged-out → rated 1–5), also written to `cost_log.jsonl` under `funnel`. Per-stage costs (`reference_summary`, `extraction`, `rating`, `salary`, `salary_estimate`) in `cost_log.jsonl`. Each job's Salary Conversion and Salary Estimate are logged on one `Pay display:` line, with the rate, its date and the estimating model. **Stage 1b cost is also reported per query** (`_scrape_per_query` → funnel `scrape_per_query`, plus a `Stage 1b cost: "<query>" $X over N iteration(s)` log line carrying prompt/cached/output tokens), because a scraper regression was previously visible only as a stage total — which is how a 68% → 99% drift went unnoticed for weeks. On the OpenRouter path `cached_tokens` from `usage.prompt_tokens_details` feeds the existing `cache_read_input_tokens` field so the two providers stay comparable. New `ui_alerts` kinds: `empty_harvest` (harvest errored or returned nothing), `blocked_click` (a results-list click refused in code), `model_reported` (the model called `report_problem`), and `provider_fallback` (the OpenRouter scraper failed and the Anthropic one ran). Cost is charged **per session**: `total_cost_usd` is cumulative within a `ClaudeSDKClient` session, so only the increase over that session's last reported value is billed (`cost_delta_for` in `agent.py`, keyed on `session_id`). Stage 1b shares one session across all queries and was previously over-counted ~3.5x; stages that open a fresh session per call were always correct. Token counters in `msg.usage` are per-request and keep summing. Every `ResultMessage` is logged with `session_id`, `num_turns`, usage, and `cost_reported` vs `cost_charged` — previously these went to the `rich` console only and never reached the run log, which is why the over-count went unnoticed for nine runs. Every `ResultMessage` **also** logs `is_error`, `subtype` and `api_error_status`, and an errored one emits a dedicated ERROR line: an HTTP-level API failure is reported by the CLI as `is_error=True` with `subtype="success"`, so without those fields an errored result is indistinguishable from a good one — which is exactly how nine identical `error result: success` warnings stayed undiagnosable (2026-08-24). **`api_error_status` is the only field that separates 401 from 429 from 529**, so any new `sdk_query` loop must run `_raise_if_result_error()` rather than testing `structured_output` alone, which silently reads an error as an empty result. - **Account safety** — Stage 1b drives a **real logged-in LinkedIn account** through the shared Playwright profile (`~/.linkedin-agent-profile`), and a flagged or banned account ends the job search permanently. This outranks coverage, cost, and run time: a slow incomplete run always beats an aggressive one. All scraping goes through the Playwright profile; never scrape from the user's own browser. Specifically:
  - **The browser toolchain version is pinned** (`PLAYWRIGHT_MCP_VERSION`), never `@latest`. `@playwright/mcp` is the entire tool surface the scraper drives that account through, and the snapshot-mode and tool-count facts recorded under Cost efficiency hold for one specific bundle. An unpinned spec lets that change with no commit and no test failure — and it already stopped a run dead at an npx install prompt (2026-09-01). `npx --yes` is safe only *because* the version is exact: it can install nothing but the pin. Upgrades are proposed at startup by Check Browser Toolchain Version and applied by editing the constant, so a new bundle is always watched through one live search before it runs unattended
  - **Nothing in the job results list is ever clicked.** Not a card, not a title, not a logo. The only real `<button>` in a row is **Dismiss**, which the accessibility tree disguises as the card itself, and one stray click permanently removes a job from the User's feed — this already happened, to three real jobs. Clicking is also unnecessary: Harvest Job Listings reads everything from the DOM. This is an invariant, not a preference. On the OpenRouter path it is **enforced in code**, not merely prompted: `_guard_call()` in `scrape_openrouter.py` refuses any `browser_click`/`browser_hover` naming `job-card-component-ref`, `SearchResultsMainContent` or `Dismiss`, and any `browser_evaluate` that clicks or dispatches events — each refusal logged and counted as a `blocked_click` alert. This is not theoretical: on 2026-08-21 the model tried to drive the page with JavaScript `.click()` and was refused. Unit tests assert both the guard and that the prompt states the rule
  - **JavaScript may read the page, never drive it** — `browser_evaluate` for extraction and scrolling only; never to click, submit, or dispatch events. `LINKEDIN_PAGE_CAPTURE_JS` only serializes the DOM; a test fails if it ever contains a click, event dispatch or DOM write
  - **No Stage 2 model drives the browser** (2026-09-24). Code navigates and reads each job page; the OpenRouter extractor's only tool is `submit_job_extract`. The model-decided "… more" click is gone with it — the description was always complete in the DOM without it
  - **Never apply, save, follow, or dismiss** anything
  - **Randomised pacing** between searches (`SCRAPER_INTER_SEARCH_DELAY_SECONDS`) and between queries (`SCRAPER_INTER_QUERY_DELAY_SECONDS`). Every delay is a **(min, max) range drawn uniformly** — a fixed interval is itself a robotic signature, and a unit test rejects degenerate ranges. Inter-query pacing is enforced **in code** (`_human_pause`), not merely prompted, because a model under turn pressure will skip a prompted wait. There is no per-listing delay any more: harvesting is one read-only call, so there is no interaction burst to disguise
  - **Stop on any CAPTCHA, verification challenge, or "unusual activity" notice** rather than work around it, and the recovery pass explicitly refuses to retry into a block. A challenge means LinkedIn already suspects automation; solving or immediately retrying converts a soft signal into a confirmed evasion pattern, which is what escalates to a restriction. Backing off keeps it a blip — the 2026-08-06 run went 0 listings at 11:43 and 74 at 12:08 after a pause. This applies only to *challenge pages*; zero results or a slow load still get a normal retry
- **Search coverage** — every generated Search Query must actually be searched, once per configured region. Stage 1b sends one request per query (own turn budget) on one shared session (one browser attachment); the run audit log distinguishes "never searched" from "searched, found nothing", which a single `0 jobs` count cannot. Turn starvation is silent — the model stops mid-query and the run still reports a listing count — so `SCRAPER_MAX_TURNS_PER_QUERY` is set with headroom: harvesting is one call per search, but each listing still costs a `check_and_record_job` (and possibly a `queue_candidate`) turn, so the budget scales with `SCRAPER_MAX_LISTINGS_PER_SEARCH` × regions, and `num_turns` is logged per request to make exhaustion visible. **Under-coverage is detected by yield and by turn usage, not only by a zero count**: a query below `SCRAPER_MIN_LISTINGS_PER_QUERY` is retried, and one that stops well short of its turn budget is warned about. Stopping *early* is as much a failure mode as running out — on 2026-08-11 every query used 10 of 90 turns and returned exactly one listing, and a `seen == 0` trigger missed all of it **Filter state on the results page is fragile.** Once a filter chip has been clicked, never navigate again. Navigating drops the `geoId` while the sticky location chip keeps *displaying* the region, and `check_filters_applied` then fails. A restart must re-click every chip, location included. The account's salary param (`f_SAL=f_SA_id_227001:277001`) reappearing after "Show results" is expected (2026-09-10). The location is sticky across sessions, so it is set on every search. Known `geoId`s: Canada `101174742`, European Union `91000000`. Moving the region from the query text to the chip took yield from 1 never-seen job in 12 searches to 30 in 2 (2026-08-18)
- **Rejection auditability** — `python main.py -n --audit` runs normally but additionally re-rates every gate-killed Job Posting (hard-ruled or triaged-out) with the strong rater, logging any **false negative** (gate dropped it but the strong rater scores ≥3) plus a run-end count. Diagnostic only — saving/notification behaviour is unchanged **Do not loosen the gates after a quiet run.** A `--audit` run over 25 candidates found 0 false negatives; all 25 listings were new and all 25 extractions succeeded, yet only ~12% scored 4/5 (2026-07-23). "Not finding jobs" is a low base rate plus variance. The leverage is in Stage 1: query relevance and filter yield
- **Resilience** — classify each failure by what it breaks, and handle each class once. Classify HTTP failures on the **status code**, never the reason phrase.
  - **Optional server down** (Ollama :8002, OpenRouter :8006): quiet fail-open, no alert. Summarization falls through its provider chain (last resort: the full reference block), and triage passes jobs straight to rating.
  - **Misconfiguration**: detect once per run, never once per job. A missing `OLLAMA_MODEL_NAME_TRIAGE` is caught by `preflight_local_model()`, which logs one ERROR naming the installed models, raises `local_model_missing`, and disables triage for the run (2026-08-25: ten days of silently dead triage). Pin a concrete Ollama tag. `:latest` is not a moving alias, and a re-pull can make it vanish.
  - **An endpoint that answers but cannot do the job is dropped like one that refuses** (2026-10-02). A 429 moved the run from streamlake/fp8 to open-inference/fp8, where the model re-announced "let me examine the current page state" turn after turn without progressing, wrote ~1,600 completion tokens per turn against ~125 on StreamLake and ~230 on Morph (all Stage 1b passes 2026-09-21..10-05), took minutes per turn and hit the `chat` timeout three times. None of that was a failure to the code, so the run stayed on that endpoint for 6.5 hours: three queries reached `SCRAPER_OPENROUTER_MAX_ITERATIONS` with 0 listings, twice each, and a real account was driven aimlessly throughout. Two rules, both ending in `ProviderPin.switch` (so both are capped by `SCRAPER_PROVIDER_MAX_SWITCHES` and raise a `provider_switch` alert): a `chat` call that times out on a pinned endpoint drops that endpoint and is asked once of the next; and an endpoint averaging more than `SCRAPER_MAX_COMPLETION_TOKENS_PER_ITERATION` completion tokens per turn, once it has served `SCRAPER_VERBOSE_MIN_ITERATIONS` turns of a pass, is dropped for the rest of the run. Why that endpoint behaved this way is not known.
  - **Provider refusal** (401/402/403/429) breaks every query: `ProviderUnavailableError` aborts the query loop and the caller falls back to the Anthropic scraper. Queries never reached are marked `'error'`; a query the fallback then re-runs sheds that mark and its `_query_errors` entry, or a fully searched query reads as failed (2026-09-28: "4 of 6 QUERIES FAILED" on four queries the fallback had searched). The fallback costs ~9x per search, so it always raises a health alert (2026-09-02: out of OpenRouter credit mid-run). **The fallback runs only the queries OpenRouter did not finish** — those with no integer count in `_queries_searched` — and does not start if none are left (2026-09-28: the 429 came on query 3 of 6 and the fallback re-scraped queries 1 and 2 too, doubling their LinkedIn traffic; under `SCRAPER_ANTHROPIC_FALLBACK_MAX_COST_USD` that re-scrape would consume the budget before the unfinished queries were reached). The `provider_fallback` alert states how many queries it covers.
  - **Every LLM MCP call sets its own wall-clock cap** (`LLM_MCP_CALL_TIMEOUT_SECONDS`). The shared client's 30s default is for quick sends only. Moving onto the shared `mcp_client` silently gave every chat/generate call that 30s cap, which a Stage 1b round with a large conversation regularly exceeds. On 2026-09-14 that lost 4 of 6 queries and most of Stage 2 to `timed out after 30.0s` while the server was healthy. Pinned by `test_llm_mcp_call_sites_pass_long_timeout`.
  - **Transient gateway error** (500/502/503/504, `TRANSIENT_HTTP_STATUSES`, disjoint from the abort set): retry the same chat call once after `TRANSIENT_RETRY_DELAY_SECONDS`, then fail that query only (2026-09-10).
  - **Truncated response** (`finish_reason == 'length'`): `rate_with_openrouter` retries once. Never repair truncated JSON. **When the rating call fails, a different model is asked; a malformed reply is never repaired** (2026-10-09): `rate_job` works down `MODEL_NAME_RATING` and then each of `MODEL_NAME_RATING_FALLBACKS` on any failure of a call, including a complete reply that is not a usable rating (`MalformedRatingReplyError`), and never asks one model twice. The fallbacks are other flash-tier OpenRouter models, so a fallback rating costs about what a normal one does; an OpenRouter outage fails all of them, and the job is then released for the next run. The result's `rated_by`, the `Rating` log line and funnel counter `rating_fallback` name which model answered. On 2026-10-08 a reply holding `"rating": 5` left its last array unclosed — not truncated, so the truncation retry never saw it. **An `eval_error` is no longer terminal**: the job is already in `processed_jobs/`, so Stage 2 releases it for the next run through `release_errored_job()`, at most `EVAL_ERROR_MAX_RELEASES` times per job (counted in `run_dir/eval_error_releases.yaml`), because a posting that fails every time must not be opened on the real account on every run. Past the cap, or when the release itself fails, the ERROR line says the job is not retried. Funnel counter `eval_error_released`. A posting scored 5 was lost to a terminal `eval_error` on 2026-09-04 and again on 2026-10-08.
  - **Per-item vs systemic**: a corrupt PDF or a page that will not load warns and continues. An API-level failure aborts the loop, since the next item would fail the same way (2026-08-24: one API failure spawned nine doomed categorization subprocesses).
  - **The browser dies mid-run** (2026-09-21: `@playwright/mcp`'s node process hit a V8 heap OOM 1h38m in; the macOS crash report under `~/Library/Logs/DiagnosticReports/node-*.ips` was the only record of the cause). A dead browser is a systemic failure, not a per-job one: every remaining job then fails within milliseconds with `All connection attempts failed`, and 23 were logged as `eval_error` and lost to dedup. `BrowserServer` is checked before each job and after each failure. After a failed extract, `confirm_dead()` also **probes the port**: the exit status alone is not enough, since on 2026-09-28 the server dropped and the last 3 jobs failed within 43 ms, before the exit was reaped, and were written off as bad pages. A restart first stops a server that stopped answering but is still running. It is restarted up to `PLAYWRIGHT_MAX_RESTARTS_PER_RUN` times and the job it died on is retried. Past that, Stage 2 stops with one ERROR line and hands the unevaluated jobs back (see Idempotency). A job failing on a dead browser is never counted as `eval_error`.
  - **Cleanup must not raise on something that already failed.** `asyncio` `Process.terminate()` raises `ProcessLookupError` on an exited process, and in that same 2026-09-21 run it escaped the `finally` block, so the run ended with no summary, audit log, cost-log entry or Telegram message. `BrowserServer.stop()` terminates only a live process.
  - **A fallback nobody tests is not a fallback**: an `except` never fires if a lower frame has already swallowed the exception (2026-09-02).
  - **Fail open or closed depending on what already matched**: the blacklist fails closed (a name the user wrote down already matched, and an outage must not readmit it). The location classifier fails open (it runs only when nothing the user wrote down matched, and an outage must not start excluding jobs). Review Country Lists and Guess Unbucketed Location fail open — a failed guess records nothing, and the posting that raised it was already kept. A corrupt `location_recommendations.yaml` is skipped, not rebuilt, because it holds the user's own decisions. The recruiter-repost check fails **open** for the same reason as the classifier: nothing has been established except that the same agency posted before, so an outage must not silence a real role — and an unreadable `recruiter_notifications.yaml` is treated as empty rather than preserved, because it is rebuilt by the next notification and must never be able to *suppress* one
- **Idempotency** — processed-job records persist across runs so jobs are never evaluated twice; applied-job ingest is a no-op for already-dated files. The one deliberate exception: a job Stage 2 never evaluated because the browser stayed dead has its record deleted (`forget_processed_job()`), since a record written at queue time would otherwise dedup it away forever (2026-09-21)
- **Applied-date durability** — an Applied Job Record's date is carried by the filename prefix, `index.yaml`, and mtime independently, so it survives a move, copy, or backup restore that drops filesystem metadata

It now matches `COMPANY_BLACKLIST_EXPIRY_DAYS` so both lapse rules read alike. Widening it costs nothing in rating quality: the ideal-role profile is the `MAX_REFERENCE_JOBS` newest-applied records regardless of the window, so only the blocklist and the query-generation prompt grow. It does enlarge the fuzzy company-match candidate list, and that match fails closed — see Known open issues
- **Notification latency** — Telegram alerts sent immediately when a job is rated 4 or 5 during evaluation. The one job rated 4 or 5 that sends no alert is a recruiter repost of a role already sent (see Suppress Recruiter Repost); it is still saved, and says so in the Saved Job
- **Rating hard rules (applied in code before any LLM scoring)**: a company on the user's Preferences **blacklist** (poster or end client) → 1; closed postings → 1; postings older than `JOB_STALE_AGE_DAYS` → 1; jobs in a `sponsorship_required_in` location with no sponsorship offered → 1; a required language outside `languages` → 1; a hard requirement for a degree in `reject_required_degrees` → 1. a `location` whose every named country is on `locations.would_not_live_here` → 1; a stated `relocation` to such a place → 1. **For a `remote` posting the anchor rule is conditioned on `residency_scope`**: it fires when the JD pins residence to the anchor country, and otherwise only when a country the posting names is outside the EU — a silent `Poland (Remote)` is kept, a silent `United Kingdom (Remote)` is not. `hybrid`/`onsite` and the `relocation` rule are unconditioned. All but the closed/stale rules are preference-driven and disabled when their lists are empty. The blacklist is the one rule here that is not purely deterministic — an exact case-sensitive name hit costs one cheap LLM confirmation call, and that call **failing rejects anyway**; it is also the only rule the user authors by hand, is unrelated to the automatically derived already-applied blocklist, and an **expired** entry (`COMPANY_BLACKLIST_EXPIRY_DAYS` after its `added` date) does not reject. Required relocation is **flagged rather than rejected for an acceptable location**, and rejected only when it names a place on `would_not_live_here` — the narrow exception, because there the JD is asserting a categorical requirement rather than code inferring one from a location string. The geographic rules are the second pair here that are not purely deterministic: an unlisted location costs one cheap **cached** classification, and unlike the blacklist that call **failing fails open** (nothing the user wrote down had matched). The degree rule fires **only on hard requirements** — "MSc preferred", "Master's or equivalent experience", and "Bachelor's or Master's" all survive, because an auto-reject is unappealable and a posting that would accept experience instead must never be killed. **Being posted by a recruiting agency is not a hard rule and not a rating cap.** It warns, and it gates Suppress Recruiter Repost, which can withhold a *repeat* notification for a role already sent — never the first one, and never the rating. Applying once through a staffing firm must never suppress the other companies it posts for, and an agency posting can be an excellent role (CyberCoders rated 5/5 on 2026-08-11). Two unit tests pin this: the rating is identical with and without `is_agency`, and an agency posting is never hard-ruled
- **Rating caps (applied deterministically in code AFTER LLM scoring)**: two ceilings, both in `apply_rating_caps()` — a `hybrid`/`onsite` Job Posting whose location is not on Preferences `locations.would_commute_here` is capped at `hybrid.rating_cap`, and a Job Posting whose `posting_language` is outside Preferences `languages` is capped at `foreign_language_rating_cap`. When several apply the **lowest wins and every applicable reason is reported**, so the log line and the saved job name everything that held the rating down. A cap is a **ceiling, not a rejection or a floor** — the job is saved, recorded, and auditable, and a rating already at or below the cap is untouched; it simply cannot reach the ≥ 4 notification threshold. The caps exist because the prompt alone is not sufficient: the evaluator rated a hybrid role in an unacceptable location 4/5 while naming the hybrid location as a drawback in its own reasoning, and rated a French-language posting 4/5 after translating it into English while condensing. Every cap is logged (`Rating capped: … 4 → 3 (reason)`) and counted in the run funnel as `rating_capped`

  in-person all mean uncompensated travel time *and* permanently living within reach of that office.
  The evaluator prompt says so in those terms, and `_ONSITE_RE` was extended to the phrasings that
  previously resolved to `''` (`on location`, `office-based`, `work from our offices`, `presence in
  the office`) — which earned them the remote benefit of the doubt **and** no commute cap at once.
- **The agent may write exactly one preference list, and only because that list gates nothing** —
  `locations.not_yet_bucketed` holds guesses awaiting the user's decision. The append is textual,
  written to a candidate string, re-parsed, and only then swapped in; the file is hand-written with
  20 comment lines and the project has pyyaml only, whose `safe_dump` would delete every one of
  them. **Renaming any preference key requires a legacy guard in the same change**: `_deep_merge`
  silently ignores what it does not recognise, so a stale key leaves the list empty and switches
  its rule off with no error anywhere — `load_preferences()` raises on each old name instead.
- **Names stay proper; fold at the comparison, never at the store** — `EU` not `eu`, `Málaga` not
  `malaga`, `Spain` not `spain`. Case-folding is a lossy transform: you can always `casefold()` a
  name at the point you compare it, and you can never recover the case afterwards. So a name keeps
  the case it arrived with all the way through — the classifier's `countries` and `place_names`,
  the preference lists (`locations.would_live_here`, `locations.would_not_live_here`,
  `locations.would_commute_here`, `sponsorship_required_in`), `end_client`, blacklist entries — and each comparison folds locally
  if it needs to (`is_eu_member`, the sponsorship substring test, `undecided_countries`).
  **Controlled vocabularies are the deliberate exception and are stored folded**, because they are
  identifiers rather than names: `regions` (`southern_europe`), `languages`, `workplace_type`,
  `education_requirement`, `residency_scope`, `reject_required_degrees`. Cache keys fold too
  (`cache_key`), because a key is not displayed. This is not a style rule — it was violated twice
  in one change and cost real behaviour both times: lowercasing the location lists made `malaga` an
  entry that could never match `Málaga`, and lowercasing the classifier's `countries` while the
  lists held proper names made `undecided_countries` report **every** already-decided country as
  undecided, sending each to the LLM on every run while the "zero calls in steady state" claim
  still read as true. Regex literals follow the same rule (`_AREA_WORDS` / `_EUROPE_WORDS` say
  `EU`, `EMEA`, `Schengen`; `_US` says `U.S.`) even where `re.IGNORECASE` means the case does no
  work — reading `emea` in source gives no hint whether it is an acronym, a country or a typo, and
  a place name is written once as a named constant rather than re-spelled inline per pattern.
  **Never `.title()` a place name for display**: it already has its case, and `.title()` turns
  `USA` into `Usa` and `McLean` into `Mclean` (languages are the exception — a folded vocabulary
  that `.title()` presents). Test fixtures standing in for classifier output or the user's lists
  use proper names too, or they test a matching rule production does not have.
- **A matching rule fails silently permissive** — a bad list entry leaves no anomaly anywhere: the log line for a job it wrongly exempts reads exactly like the line for a genuinely acceptable one. `roma` on the exempt list matched every Romanian posting while Bulgaria, Poland, Czechia and Lithuania were rejected correctly in the same run, and two Romanian roles were notified (2026-09-09). The exempt tier short-circuits before the classifier, so the cache held no trace of the jobs it exempted. That is why Review Country Lists accumulates countries per run on the cache-hit path too. The matching rules and their tests are under Reject Excluded Location. **A presence check on a free-text field must test for the value, not the string.** The extractor writes `Not specified`, `Competitive salary` or `Not stated ("competitive compensation")` into `salary` instead of leaving it empty, and `if not extract.get('salary')` read all of them as salaried: 196 saved postings got no missing-salary warning, more than the 166 that did, and nothing anywhere looked wrong. `salary_figure_listed()` now requires a digit (2026-09-15). **And a presence check is not a completeness check.** "Is there a digit" is equally true of `CA$208,580-$273,770`, of `Up to €50k`, of `Minimum €65,000`, of `€110,000` and of `12-month contract / Outside IR35`, so a range with one end was indistinguishable from a range with two and the warning stayed silent: 93 of the 911 figured postings in the saved corpus state only one bound, and a few state no pay at all. Job 4470298356 was notified 4/5 with the only salary text reaching the user being the rater's own bullet, which led with the floor (2026-09-22). Structure is now read in code by Classify Salary, and the reading — not a digit — decides the warning. **A token matched without boundaries matches inside words** (2026-10-08): the currency regex was case-insensitive and unanchored, so `Toronto: $120,000` read as RON, `Europe: 80,000 GBP` as EUR and `Academy bonus` as CAD. It went unnoticed because the only consumer, the target comparison, merely abstained on a wrong currency; it surfaced the day a reading's currency was about to drive a converted figure shown to the user. Alphabetic tokens now need a non-letter on both sides, and a bare `kr` (SEK, NOK, DKK, ISK) is left unresolved like a bare `$`. A field nothing depends on is not thereby correct
- **Code hygiene (2026-09-21)** — three rules, none left to judgement:
  - **Never swallow an exception.** Every `except` raises with context (what was being done, on which input, the exception type and message, `from ex`), or logs through `logger` with that same context, or both. Returning a default, `continue`, `pass`, or a `console.print()` alone is swallowing: the console never reaches the run log. Helpers called many times, such as parsers and converters, **raise**, and the caller that knows the job, file or run logs once. `parse_posting_date`, `_parse_iso_date` and `_parse_added_date` return `None` only for input that was not given.
  - **No magic numbers.** Every numeric literal other than 0, 1 and -1 is a named constant, usually in `config.py`, including slice bounds, timeouts, poll counts, HTTP statuses (`HTTPStatus`) and display widths. Docs name the constant and never restate its value: `SCRAPER_MIN_LISTINGS_PER_QUERY` was documented as one value while the code held another.
  - **No silent truncation.** A cap on text sent to a model goes through `text_budget.truncate_reported()` or `pages_to_prompt()`. Each logs a WARNING naming what was cut and by how much, and appends a marker so the model knows its input is partial. Display excerpts go through `snippet()`, which says how much it hid. **Deterministic checks are never truncated**: the residency, workplace, degree, agency, contract and salary regexes scan the whole description, because regex over the full text is free. **And a cap that always drops the tail is not neutral when the fact lives in the tail.** A job description keeps compensation, benefits and work-authorization statements at the bottom, and one LinkedIn a11y snapshot measured 74,797 chars against a 40,000-char cap and lost 34,797 of them from the END — including, plausibly, the pay range a notification then reported without any way to check it (job 4470298356, 2026-09-22). A snapshot is therefore collapsed (whitespace is not content in an accessibility tree) before anything is dropped, budgeted against its own `EXTRACTOR_SNAPSHOT_MAX_CHARS` rather than the shared tool-result cap, and cut from the MIDDLE by `truncate_reported_middle()`, whose marker names how much went and from where. Every other tool result still loses its end. **Stage 1b removes what it may not read before it caps** (2026-09-30): a search-page snapshot loses its job detail pane (`snapshot_prune.drop_job_detail_pane()`, anchored on `SNAPSHOT_DETAIL_PANE_HEADING`) and is then capped at its own `SCRAPER_SNAPSHOT_RESULT_MAX_CHARS`. The pane is a posting Stage 1b never reads, yet it inflated every one of 662 logged snapshot truncations, and the cut that followed fell inside the result cards. The removal is logged at INFO and leaves a marker in place of the pane. It never touches the chip row, the results count or any card: a pane that cannot be separated from them, or a page with no search UI at all (a single job's page), is left whole, so the cap and its WARNING still apply.

  Why: PDF categorization read only `text[:3000]` of the raw extraction, whitespace included, so a PDF that opened with padding was categorized from nothing, and nobody was told. The same literal `3000` was copied into the reference-job block and the applied-job metadata call. Meanwhile the regex gates above scanned only the first 2000–4000 chars of a description, so a requirement stated late in a posting was silently missed. The run that surfaced this aborted on an API error (a lapsed login, no HTTP status), and a second `aclose(): asynchronous generator is already running` traceback buried it. Raising inside `async for … in sdk_query(...)` left the SDK stream open, so every `sdk_query` loop now runs inside `contextlib.aclosing()`, and `_raise_if_result_error` names the login as the likely cause when no status is reported. The same review found the Playwright readiness poll doing `except: pass` and carrying on after every attempt failed; it now terminates the server and raises.
- **Tests must be able to fail** — each rule here comes from a test that stayed green while the thing it guarded was broken:
  - **A skip that never turns into a pass is not a passing test.** `live_agent_claude` was gated on `ANTHROPIC_API_KEY`, which the SDK does not need, so every live test silently skipped. Turning it on exposed two real `src/` bugs (2026-08-24). Inside the Bash sandbox, `connect_ex` to 127.0.0.1 is always refused, so live LLM tests always skip there: run them with the sandbox disabled or they are decorative (2026-08-25). A stub that fails open is the same shape one layer down, which is why `tests/conftest.py` stubs the location classifier.
  - **Fixtures must not be cleaner than reality.** Fixtures without playwright's `### Ran Playwright code` echo let a parser that returned None on every real harvest stay green (2026-08-21).
  - **Tests read the constant, never a copy of it.** `test_generate_local_live` hardcoded `qwen3.6:latest`, so it could not have noticed the tag vanishing (2026-08-25).
  - **Assert which records survive, not how many.** A count-only cap test passed while the code kept exactly the wrong 20 reference jobs (2026-08-25).
  - **A test double must not be more careful than the code it doubles.** The `_GEO_RE` in `conftest.py` was word-boundary anchored while production matched bare substrings, and nothing compared the two (2026-09-09).
  - **Reset module globals per test, and never reset one after startup code has appended to it.** This is the most-repeated bug in this project. `run_non_interactive()` reset `_ui_alerts` and discarded a startup alert it had just been given, which is why `_startup_ui_alerts` exists (2026-09-01).
  - **What prose cannot enforce, a test must.** A note scoped to "in `agent.py`" left four `ClaudeAgentOptions` sites in `tools_generic.py` unfixed for three months, and `test_every_claude_agent_options_site_limits_context` now walks the AST instead
- **Dependency pinning** — dependencies that change behaviour are pinned: `PLAYWRIGHT_MCP_VERSION` (see Account safety). `mcp` was pinned below 2 until 2026-10-07: a bare `uv run` had re-resolved `mcp>=1.29` to 2.0.0, whose `streamable_http_client` yields two values instead of three, and that broke every OpenRouter and Ollama call mid-run (2026-08-21). **A pin must name the code that depends on it, and be re-checked when that code moves.** The tool-server client later moved to a raw-httpx implementation in `utils_tools_n_agents_common.mcp_client` that imports no `mcp` at all, so the pin and its two tests guarded nothing; both were removed, the direct `mcp` dependency was dropped, and `mcp` now arrives only through `claude-agent-sdk`, which bounds it. `npx @playwright/mcp@latest` re-resolves on every run, and npx's cached `^0.0.79` means exactly `0.0.79`, since caret does not widen below `0.1.0`. So an upstream release blocked a scheduled run on an install prompt (2026-09-01). Compare versions numerically: `0.0.9` sorts after `0.0.79` as a string and before it as a version
- **Knowledge locality** — project decisions, diagnoses, and conventions live in tracked repo files. Machine-local paths (including `~/.claude` and its per-project memory directory) are never used for project knowledge, because they do not reach another machine. `run_dir/` is the one deliberate exception: gitignored because it holds personal data (resume, applied-job PDFs, saved postings, `JOB_REQUIREMENTS.md`, `preferences.yaml`)
- **No personal information in tracked files** — nothing in git may identify or describe whoever is running the agent: no home location, work-authorization or immigration status, languages, education, employers or recruiters dealt with, compensation targets, or absolute paths containing a username. Every such fact is a **preference**, and preferences live only in `run_dir/preferences.yaml`. Tracked code reads them through `preferences.py` and must behave sanely when they are absent — the defaults are neutral, so an unconfigured checkout applies no work-authorization, language, or education gate rather than inheriting someone else's situation. Tests pin their own fixed preferences in `tests/conftest.py` and must never read the real file. When adding a rule that encodes a personal fact, add a preference key; do not hardcode the fact. The region vocabulary in `location.py` is the boundary case worth naming: *which* regions exist is world knowledge and belongs in tracked source, while *which* of them the user will not work in is personal and lives only in `preferences.yaml`
- **Known open issues** — recorded so they are not rediscovered:
  - **Interactive mode probably cannot call its own MCP tools.** `permission_mode="acceptEdits"` auto-approves file edits, not in-process MCP tools, and `main()` sets no `can_use_tool` or `allowed_tools`. So `save_job_posting`, `check_and_record_job` and `update_job_requirements` should all be denied, which shows up in `ResultMessage.permission_denials`. It is deliberately unchanged: interactive mode also holds the logged-in LinkedIn browser, so widening its permissions is an Account safety decision (2026-08-24).
  - `--snapshot-mode none` for `@playwright/mcp` is not applied (see Cost efficiency).
  - **`@playwright/mcp` 0.0.82 may leak heap.** Its first run died of a V8 OOM after 33 Stage 2 extracts, where the last run on 0.0.81 completed 75 (2026-09-21), and `PLAYWRIGHT_MCP_VERSION` was rolled back to the previous release the same day. Re-tried 2026-09-23 after a watched run on 0.0.82 completed clean — 6 queries / 300 listings in Stage 1b, 24/24 Stage 2 extracts, no `browser_restarted`, no OOM — but that pool was smaller than the day the browser died, so the extract count never passed 33 and the leak is neither confirmed nor cleared. Keep the check alive: after runs on 0.0.82 or later, verify the run had no `browser_restarted` alert, and keep noting each run's extract count until one passes the old death point.
  - Provenance validation for `submit_job_extract` is designed and **partly** implemented: Check Salary Provenance verifies the one field whose fabrication is known to have reached a user, against the retained page. Title, company and enum validation are still unbuilt (see Anti-fabrication).
  - **The Anthropic agentic extract path retains no raw posting text.** `extract_job_page()` never holds the snapshot — the SDK session does — so a job extracted that way has nothing for Check Salary Provenance to compare against, and the check passes it by default. Only the OpenRouter loop (the default) and the deterministic fallback retain.
  - **A bare `$` is not resolvable deterministically** (USD, CAD, AUD, SGD), so a Salary Reading of `$190K/yr - $300K/yr` carries an empty currency. It is not guessed: an unresolved currency does not make a range incomplete, and nothing compares the bounds against a target.
  - **Whether the lululemon figures were ever right is unknown.** `CA$208,580-$273,770` cannot be checked against the live posting, because nothing local retained the page (2026-09-22). That is what Retain Raw Posting Text fixes going forward; the original reading stays unverifiable.
  - The deterministic extraction fallback (`extract_job_page_direct()`) captures neither `is_agency` nor `end_client`. A posting that falls through to it is left with the regex that catches about 1 in 10 agency postings (see Flag Agency Posting) — and since that flag is the gate on Suppress Recruiter Repost, such a posting is not compared against earlier ones either, so a repost of it can still notify twice.
  - Nobody has tested whether the self-injected salary param `f_SAL` narrows results (see Search coverage)
  - **A non-agency company reposting the same role under a new LinkedIn job id is not caught.** `(site, job_id)` dedup is keyed on the id, so a repost reads as a new job, and `RECRUITER_REPOST_WINDOW_DAYS` only ever runs for `is_agency: true`. While the company is inside the applied-job horizon the already-applied blocklist hides it; once the horizon lapses, nothing does. GitLab's "Distinguished Engineer, Agentic SDLC & Non‑Linear Productivity" sits in `processed_jobs/` three times — `4411658716` (2026-05-07, the one applied to), `4466425326` (09-13), `4466418337` (09-14) — and the 09-13 one notified as a 5. Raising the horizon to 180 days widened the window that masks this; it did not close it. Matching a candidate against applied jobs on company + title would, but **any such matching must normalize Unicode punctuation first**: the two GitLab records differ only by a non-breaking hyphen (`\u2011`) in the title, so a literal compare fails on postings that are otherwise character-identical (2026-09-15).
  - **Hybrid and contract duplicates are suppressed by prompt only.** Salary is folded in code (`merge_salary_warning()`), but no code guard exists for workplace or contract: a token-overlap guard was tried and is unsafe, because location strings inflate the overlap — it dropped `Vancouver BC is an acceptable on-site location` against `On-site — Vancouver`, and a French-language line against a Quebec hybrid line. Expect a residual near the agency/language rate (12–25%), not zero (2026-09-15).
  - **The already-applied blocklist matches fuzzily and fails closed, with no confirmation step.** `company_matches_applied()` tries a normalized exact match for free, then asks an LLM — and an LLM "yes" suppresses the job outright, unappealably. This is the inverse of the hand-authored blacklist, which matches exactly and spends a confirmation call precisely so a same-named organization is not rejected by mistake. Two unrelated companies sharing a name (the "Cohere AI lab vs. Cohere Health" shape) would be silently skipped. Raising the horizon to 180 days took the candidate list from 58 names to 82, which makes a wrong match likelier; wrong skips surface as `already_applied` entries in the run audit log (2026-09-15).
